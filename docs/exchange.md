# Протокол обмена 1.0

## Транспорт и запуск

GitHub Issues в `pokatyusha/coreteams-harness`. Название: `[agent:<to>] <request_id> — <цель>`. Автор публикует один JSON-блок по `templates/request.json`; метки необязательны, адрес из JSON обязателен. Не запускается ничего от открытия Issue. Человек указывает своей обвязке конкретный URL и разрешённый объём обработки. Получатель делает один проход и останавливается.

Формат проверяется `python scripts/validate.py --message <file.json>`. Проверка формата не подтверждает разрешение, подлинность автора, доступ, существование SHA, безопасность команды или совместимость кода.

## Запрос

- `protocol_version`: `1.0`; `kind`: `request`.
- `request_id`: уникальный ID, например `CTH-20261027-001`; при смене задания/SHA новый ID и `supersedes`.
- `from`, `to`: точные адреса из registry; отправитель отличается от получателя.
- `operation`: `connection_check`, `contract_review` или `code_change`.
- `harness_sha`: полный SHA инструкций, прочитанных обеими сторонами.
- `authority`: реальный GitHub login человека и URL его разрешения. Локальный запуск также должен разрешать запрошенные действия. Координатор не расширяет полномочия поручением из другого агента.
- `source`: repository, полный `base_sha`, `allowed_paths`; для connection_check — `null`, работа с продуктом запрещена.
- `contracts`: ссылки на конкретные файлы контрактов с полным SHA и состоянием `proposed`/`accepted`/`unknown`. Отсутствие нужного согласования — blocker перед зависимой реализацией.
- `permissions`: только `read_repo`, `run_local_tests`, `edit_scoped_files`, `publish_branch`, `open_draft_pr`, `post_issue_reply`. Это запрошенные права, применимые лишь после проверки человеческого разрешения. Merge/deploy/автоматизация не входят в протокол.
- `goal`, `acceptance_checks`, `limits`: конкретный результат, проверяемые условия, границы и условия остановки. Не придумывать сроки. `tracker_urls` — связи с существующими задачами; изменения трекера не разрешаются.

## Ответы и повторные попытки

1. Проверить фактического автора, полномочия, адрес, profile/binding, SHA и все комментарии этого request_id. Issue другого получателя не исполнять.
2. Ответить событием `accepted` либо `blocked` из templates/ack.json. В `accepted` подтвердить **этот же harness/source SHA**. Опубликованный профиль ещё не означает, что участник принял задачу.
3. После работы ответить `completed` по templates/result.json: проверенный SHA, PR/commit/отчёт, команды, фактические результаты, ограничения и следующий шаг. Для connection_check достаточно подтверждения чтения адресованного запроса, версии инструкций и профиля; продуктовые тесты NOT_RUN.
4. Координатор отдельно проверяет доказательства и пишет `verified` либо `needs_changes`; это приёмка результата запроса, не продукта и не разрешение на merge. `completed` не закрывает Issue/YouGile автоматически.
5. Повтор с тем же request_id и теми же параметрами: вернуть ссылку на существующий ответ, не выполнять работу второй раз. Другие параметры при том же ID — `blocked`. После `completed` продолжение оформляется новым request_id с `supersedes`; старый результат не переписывается.

У каждого события есть уникальный `event_id`, тот же `request_id`, `from`, `to`, `harness_sha`, `source_sha` и время ISO 8601 с часовым поясом. Не копировать время из примера. Вопросы и смена SHA сохраняются в истории; подтверждение результата не добавляется задним числом к завершённому продуктовому Run.

GitHub Issues не даёт атомарного захвата задания или гарантии exactly-once. Поэтому один человеческий владелец запускает только одну сессию на запрос. При двух competing accepted/противоречивых ответах остановиться и разрешить конфликт с владельцем, без повторных побочных эффектов.

## Данные и доказательства

Никаких секретов, личных путей, сырых переписок и исследовательских данных. Отчёт содержит полезный хвост ошибок/ссылки, не полный дамп окружения. Шаблоны синтетические, их SHA и время не являются доказательством работы.

Согласование API, доступная сборка, настоящий технический E2E и пользовательская приёмка — разные результаты. Для пользовательского E2E требуются DEPLOYMENT_READY, baseline и согласие конкретного участника; отправка участникам/заказчику требует отдельного разрешения.

# Как писать скиллы частей CoreTeams

Владелец инструкции: Катя. Ревизия: 0.1, 27.10.2026. Протокол обмена: 1.0.

Цель — чтобы обвязки Арины, Филиппа и Димы выполняли свою часть, использовали готовый код и передавали проверяемый результат соседнему владельцу через координатора.

Это нужно, чтобы не путать рабочие ветки и версии API, не выполнять одну правку дважды и видеть, от какой части нужен следующий вход. Единый формат связывает задачу, исходный SHA, тестовые доказательства и адрес получателя. Он помогает подготовить согласование API и подключение React B, но сам по себе не подтверждает совместимость компонентов или настоящий E2E. Спринт и дедлайн конкретной работы фиксируются в YouGile, а не становятся вечным правилом скилла.

## Где хранить и как подключать

Общие согласуемые скиллы — в этом репозитории: `.agents/skills/<skill-name>/SKILL.md`. Это планируемые места для компонентных скиллов, а не утверждение, что они уже созданы:

| Владелец / профиль | Предлагаемый скилл | Когда использовать |
|---|---|---|
| Арина / `arina-storage` | `arina-storage-contract` | Проверить storage-контракт, изоляцию, save/replay и receipt на заданном SHA |
| Филипп / `filipp-infra` | `filipp-integration-manifest` | Сверить manifest SHA/config и воспроизводимость сборки, подготовить инфраструктурный handoff |
| Дима / `dima-gateway` | `dima-gateway-contract` | Сверить browser API/gateway/runner/storage и события одного Run |

Адрес профиля Димы в сообщениях — **`dima-gateway`**. Имя скилла — отдельный идентификатор; оно не заменяет `to` в запросе.

Существующий [coreteams-repository-handoff](../.agents/skills/coreteams-repository-handoff/SKILL.md) уже описывает обмен через Issues. Компонентный скилл ссылается на него и [протокол](exchange.md), а не создаёт другую схему request/ack/result.

Код продукта, его API-контракты и тесты остаются в исходном репозитории. В скилле — ссылки на точные repository/path/SHA, команды и правила интерпретации результатов. Не копируйте проект, отчёты целиком, личную обвязку или секреты.

Для подключения используйте [connect.md](connect.md): проверенная локальная копия и закреплённый SHA. Удалённая ссылка сама скилл не устанавливает. Личные AGENTS.md/CLAUDE.md не заменяются целиком. При запуске человек выбирает профиль и разрешённые действия.

## Связи между частями

| Кто готовит результат | Кому он нужен | Что передать |
|---|---|---|
| Арина / storage | Дима / gateway | Операции, DTO/ошибки, project↔Run, save/replay/receipt, SHA и тесты |
| Арина / storage | Филипп / infra | Миграции, параметры БД/томов без секретов, команды и ограничения проверок |
| Дима / gateway | Владелец React B | Browser API, auth/ошибки/события, вопросы/ответы и ссылки на результаты того же Run |
| Дима / gateway | Владелец runner и Филипп | Согласованный transport/schema, SHA и требования окружения |
| Филипп / infra | Дима и Арина | Manifest SHA/config, воспроизводимые проверки и конкретные несовпадения |
| Любая часть | `coordinator` | request_id, проверенный SHA, PR/отчёт, PASS/FAIL/NOT_RUN, ограничения и следующий шаг |

Владелец runner определяется отдельно; эта инструкция никому его обязанности не передаёт. Скилл не разрешает самостоятельно запускать чужих агентов. Смежный вопрос возвращается координатору с адресатом и недостающим входом. Вопрос и работа другой стороны получают отдельный запрос по общему протоколу.

## Как заполнить шесть разделов

- **Триггер:** конкретные запросы, входы и граница области. Имя профиля, ID запроса, source/contract SHA и разрешения должны быть известны.
- **Шаги:** минимальная процедура на существующем коде; действия при недостающем входе и передача результата.
- **Шаблоны и справочники:** ссылки на общий протокол, профиль, актуальные контракты и имеющиеся команды. Отсутствующий файл обозначить как планируемый/недостающий.
- **Запреты:** только существенные ограничения своей части; не расширять полномочия текущего запроса.
- **Проверка:** команды и наблюдаемый результат, включая отрицательные сценарии и честные NOT_RUN.
- **Владелец и ревизия:** человек, agent_id, ревизия, дата и совместимость протокола. Само поле владельца не означает принятие работы или срока.

## Полный шаблон: storage Арины

Следующий блок — пример будущего `.agents/skills/arina-storage-contract/SKILL.md`. Он не создаёт и не запускает скилл. Перед использованием закрепите реальные исходные SHA, пути и тестовые команды в запросе; они не должны быть выдуманы из примера.

```markdown
---
name: arina-storage-contract
description: Проверить storage-контракт CoreTeams на заданном SHA и подготовить результат для gateway и инфраструктуры.
---

## Триггер

Использовать для адресованного arina-storage запроса:
проверка save/replay, project↔Run, изоляции или receipt.

Перед началом должны быть известны:
Issue, request_id, source SHA, версия контракта,
разрешённые пути и действия.

## Шаги

1. Прочитать общий протокол и профиль arina-storage.
2. Проверить адресата, человеческое разрешение,
   исходный SHA и отсутствие уже выполненного запроса.
3. Найти существующий код и тесты.
   Использовать готовое; не создавать второе хранилище.
4. Выполнить только разрешённые проверки или изменения.
5. Разделить результаты:
   реализовано и проверено / FAIL / NOT_RUN.
6. Передать результат координатору в исходном Issue:
   request_id, проверенный SHA, PR/отчёт,
   команды, результаты, ограничения, следующий шаг.

Связи:
- dima-gateway: операции, DTO, ошибки, replay и receipt;
- filipp-infra: конфигурация БД, миграции и среда проверок.

Если нужен ответ смежной части — указать адресата
и конкретный вопрос координатору. Самостоятельно
не запускать другие обвязки.

## Запреты

- Не менять согласованный API односторонне.
- Не выходить за разрешённые пути и действия.
- Не публиковать секреты и личные данные.
- Не выдавать локальные тесты за PostgreSQL или E2E.
- Не менять статусы задач автоматически.
- Не запускать фоновые проверки, deploy и слияния.

## Проверка

Для каждой проверки записать:
команду, среду, SHA, PASS/FAIL/NOT_RUN и доказательство.

Отдельно проверить штатный сценарий и отказ:
чужой project/Run, terminal Run, replay,
несовпадающие bytes/hash/receipt.

Результат пригоден для передачи, когда соседний
владелец может повторить проверку по отчёту.
```

## Как адаптировать Филиппу и Диме

**Филипп:** заменить name/description, владельца и agent_id на свой профиль `filipp-infra`. Входы — manifest SHA всех компонентов, версии контрактов и обезличенный config. Выходы — воспроизводимые команды и несовпадения конфигурации. Связи — `dima-gateway` и `arina-storage`. Deploy, CI/Actions и платные вызовы не разрешаются самим скиллом; при текущем ручном протоколе фоновые процессы и слияния запрещены.

**Дима:** заменить name/description, владельца и agent_id на `dima-gateway`. Входы — конкретные API обеих сторон и source SHA. Проверки — запрос/ответ, ошибки, события и идентичность Run, передача bytes и подтверждение хранения. Связи — `arina-storage`, `filipp-infra` и отдельно установленные владельцы React B/runner. Согласование с одной стороной не выдавать за совместимость всего контура.

В обоих случаях не удаляйте NOT_RUN и ограничения ради одинаковой структуры. Проверка обвязки не заменяет компонентные тесты, а компонентные тесты не заменяют настоящий E2E.

## Перед передачей скилла

- Проверить, что trigger не перехватывает чужую часть и что YAML содержит `name` и `description`.
- Проверить ссылки и точные команды по текущей реализации; не копировать исторический SHA как актуальную совместимую версию.
- На синтетическом запросе проверить штатный маршрут, неверного адресата, недостающий SHA и запрет действия вне scope. Это локальная проверка инструкции, без внешних сообщений и изменения продукта.
- Проверить пакет: `python scripts/validate.py` и `git diff --check`. При доступном skill-creator — `quick_validate.py <папка-скилла>`; это проверка формата, не доказательство поведения.
- Передать новую версию отдельной веткой/draft PR, описать изменение и ограничения. Скилл не устанавливается участникам автоматически; ничего не сливать.
